## 2025-11-12 20:05 向量化 vs for 循环

```bash
python code/02_vectorization_bench.py
```

第一版输出（注意：这一版没有热身，且用了 `time.time()`）：

```text
两个实现结果一致: True
线程数: 8
impl            min(ms)   max(ms)
naive              26.41    168.30
vectorized          0.94      6.10
加速比: 28.1x
```

结论：4M 元素的逐元素加法，逐行 for 循环比向量化慢 28 倍。
naive 版慢在 Python 层的 4096 次算子调度，不在算术本身——两种写法做的浮点运算量完全一样。

但我对这个数字不放心，两个原因：
1. naive 的 min 和 max 差了 6.4 倍，第一次调用明显把内存分配、线程池初始化的开销算进去了；
2. 没有热身，第一次运行还包含 page fault 和缓存冷启动。

下一版加 3 次热身 + 取中位数再测一次。


`detach 后 x.grad 是 None` 这一条我特意留着：`z` 只连着 `u`，`u` 已经断图，
所以完全没有路径能回到 `x`，`.grad` 保持 None，不报错也不给警告。
这一点挺危险——断图断错了不会报错，只会静默不更新。

## 2025-11-12 09:15 重测（热身 + 中位数）

改了 `code/02_vectorization_bench.py`：3 次热身丢弃、正式跑 10 次取中位数、
换成 `time.perf_counter()`。同一台机器同一时段：

```text
两个实现结果一致: True
线程数: 8
impl        median(ms)   min(ms)   max(ms)
naive              8.62      8.42      8.86
vectorized          0.31      0.30      0.38
加速比: 27.8x
```

两个发现：

1. **加速比几乎没变（28.1x → 27.8x），但绝对耗时全塌了。**
   naive 的 min 从 26.41ms 掉到 8.42ms（中位数 8.62ms），
   vectorized 的 min 从 0.94ms 掉到 0.30ms（中位数 0.31ms）。
   说明第一版测到的 70% 是冷启动开销，比例上恰好接近，纯属运气好。
2. **naive 的 max/min 从 6.4 倍收敛到 5%。** 这才是可信的测量。

所以以后所有计时都按这个口径：热身 3 次、跑 10 次、取中位数、用 perf_counter。
这条规矩写进第 11 章比较优化器的时候也要用。

## 2025-11-12 10:02 概率实验

```bash
python code/04_probability.py
```

```text
n=10     经验均值=2.3000  偏差=0.2000
n=100    经验均值=2.5500  偏差=0.0500
n=1000   经验均值=2.4910  偏差=0.0090
n=10000  经验均值=2.4966  偏差=0.0034
n=100000 经验均值=2.5003  偏差=0.0003
```

样本量每乘 10，偏差大约降到 1/sqrt(10) ≈ 0.32 倍，符合 O(1/√n)。
实测 0.20 → 0.05 → 0.009 的比值是 0.25、0.18，比理论还快一点，属于随机波动。

多项分布那组：n=100 时 L1 误差 0.152，n=1000 是 0.041，n=10000 是 0.013。
这个量级后来在做 softmax 分类的时候很关键——验证集 1000 个样本，
准确率的统计误差就是 ±1.5% 左右，所以 0.830 和 0.845 的差别不能当回事。
